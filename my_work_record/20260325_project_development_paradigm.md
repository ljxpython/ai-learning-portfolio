# ai-agent-test-platform 当前项目开发范式说明

## 这篇记录主要补什么

这篇文档不重复写部署步骤，也不重复贴源码，而是专门补一层“怎么理解这个项目”的视角：

- 它到底想解决什么问题
- 为什么会拆成平台侧、运行时、调试前端、结果域服务这几块
- 如果后面继续开发，应该先改哪一层，再怎么一步步推进

如果把根 README 理解成“项目地图”，那这篇更像“开发范式说明书”。

## 1. 先用一句话理解这个项目

这个项目不是把平台、智能体、调试、落库全塞进一个工程里硬搞，而是把它们拆成几个职责清楚的部分，通过浅封装和稳定契约串起来：

- 平台侧负责治理
- 运行时负责智能体
- 调试前端负责快速验证
- 结果域服务负责持久化承接

这就是当前项目最核心的设计思想。

## 2. 当前项目到底解决什么问题

很多 Agent 项目最大的问题，不是“模型不够强”，而是工程边界太乱。

常见的坑基本都是这一类：

- 平台治理和智能体逻辑混写，后面谁改都恶心
- 调试入口和正式入口混在一起，出问题很难定位
- 权限、项目、审计这些平台能力反过来污染智能体代码
- 结果落库直接塞进平台主数据里，越做越重
- 本地能跑 demo，一到独立部署和容器化就开始互相牵扯

当前项目的价值，就是提前把这些坑避开。

## 3. 为什么要这样设计

### 3.1 平台侧做浅封装

当前仓库里，平台侧不是去重写智能体运行时，而是做一层上层治理和产品入口：

- `platform-api` 负责认证、项目边界、成员、审计、catalog、runtime policy/capability 等平台能力
- `platform-web` 负责工作台、管理页面、平台聊天入口和工作区交互

真正的智能体执行、graph 编排、模型装配、tools / MCP 接入，都放在 `runtime-service`。

这套做法为什么重要？

- 平台团队可以专注治理能力
- AI 开发可以专注运行时能力
- Runtime 保持自己的标准接口和开发节奏
- 后续接平台时不用重写一套智能体实现

这里的“浅封装”不是透明透传，也不是完全不管，而是只在平台层补需要的治理能力，不深度侵入 Runtime 内部。

### 3.2 功能解耦，责任单独收口

当前各部分的职责可以直接这么记：

- `platform-web`：平台工作台和管理入口
- `platform-api`：权限、项目治理、审计、运行时网关
- `runtime-service`：智能体真正的实现层
- `runtime-web`：调试入口
- `interaction-data-service`：结果域服务

这套拆法的意义很现实：

- 平台不会被智能体业务拖成屎山
- Runtime 不用硬背平台治理包袱
- 结果域不会把平台主数据模型搞脏

### 3.3 调试链路单独存在，开发效率会高很多

当前项目保留了两条主链路：

- 平台链路：`platform-web -> platform-api -> runtime-service`
- 调试链路：`runtime-web -> runtime-service`

`runtime-web` 的作用非常关键，因为它让你可以先只盯着智能体本身：

- prompt 对不对
- tools 好不好使
- MCP 接入有没有问题
- graph 编排是不是符合预期

把这些先在 Runtime 层调通后，再挂到平台入口，效率会高很多。

这也是为什么我会把“先用 `runtime-web` 调试，再接 `platform-web`”当成默认开发方式。

### 3.4 开发完成后可以无缝接回平台

这里有个特别关键的点，一定要想清楚：

你在 `runtime-web` 上调试的，不是另一套临时工程，而是正式的 `runtime-service`。

所以只要你开发时守住边界：

- 智能体逻辑写在 `runtime-service`
- 平台治理写在 `platform-api` / `platform-web`
- 结果域写在 `interaction-data-service`

那调试完成之后，再接平台入口通常就是顺滑接入，不需要重新适配一遍。

所谓“零成本、无适配”，真正成立的前提就是你别一开始就把代码写串层。

### 3.5 后面改成 Docker 部署会更自然

这套架构和后续 Docker 化是天然一致的。

因为各部分责任已经拆清楚了，所以后面：

- `platform-web`
- `platform-api`
- `runtime-service`
- `runtime-web`
- `interaction-data-service`

都可以独立打镜像、独立部署、独立演进。

也就是说，Docker 不是后面再硬拗出来的方案，而是当前解耦设计继续往前推的自然结果。

## 4. 为什么说智能体开发主战场在 `runtime-service`

后面只要是和 AI 行为直接相关的内容，默认都应该优先看 `runtime-service`：

- prompt
- tools
- MCP
- graph
- 模型参数
- 中间件
- 多智能体协作
- 业务工作流 Agent

更关键的是，`runtime-service` 已经不是一个空壳，它把很多框架性工作都提前铺好了：

- graph 注册机制已经有了
- 模型和运行时参数解析已经有了
- 工具装配和 MCP 装配已经有了
- 多模态 middleware 已经有了
- assistant / deepagent / supervisor / SQL / workflow 等多种样例已经有了

所以后面做新能力，不是从零搭架子，而是在现有骨架上往前扩。

## 5. 为什么说几行代码就能起一个简单智能体

当前 `runtime-service` 已经把最麻烦的公共部分封好了，所以一个最小 Agent 的核心逻辑可以非常薄。

本质上你只需要：

1. 写自己的 tool
2. 写自己的 graph 装配
3. 注册 graph id
4. 跑最小验证

如果只是先做一个简单能力，这套成本是很低的。

仓库里也已经给了现成思路：

- 最小推荐范式：`assistant`
- 多任务分解参考：`deepagent_demo`
- supervisor 协作参考：`personal_assistant_demo`
- 业务工作流参考：`usecase_workflow_agent`
- 服务化最小案例参考：`sql_agent`

所以后续开发最忌讳的一件事，就是无视现有样例，自己重新发明一套结构。

## 6. 以后继续开发，建议按这个顺序推进

### 6.1 先判断需求属于哪一层

先做最基本的边界判断：

- 平台治理类需求：去 `platform-api` / `platform-web`
- 智能体行为类需求：去 `runtime-service`
- 调试验证：先用 `runtime-web`
- 结果落库和查询：去 `interaction-data-service`

这一步判断错了，后面基本全乱。

### 6.2 先把 Runtime 能力做通

新增智能体时，默认顺序应该是：

1. 在 `runtime-service` 里选一个最接近的范式
2. 做 graph / tools / prompt / workflow
3. 注册到 Runtime
4. 做最小接口验证
5. 用 `runtime-web` 做交互验证

### 6.3 再决定要不要挂平台入口

等 Runtime 稳定后，再决定平台侧要不要补：

- 管理页面
- 平台聊天入口
- project 维度控制
- catalog 管理
- 审计与权限治理

平台侧的定位永远是治理和入口，不是智能体主实现层。

### 6.4 需要持久化时，再接结果域服务

当某个智能体开始进入正式业务流，需要结果落库、查询、详情展示、审批后持久化时，再把对应能力接到 `interaction-data-service`。

这样做的好处很明显：

- 平台主数据保持干净
- 业务结果独立演进
- Runtime 通过明确的 HTTP 契约调用，不会把数据职责写乱

### 6.5 最后再考虑独立部署

边界守住之后，部署就顺了：

- 本地联调按当前多服务方案跑
- 后续容器化按服务独立拆分
- 哪块变化快就单独发哪块

所以别一上来就死盯 Docker，先把架构边界守住更重要。

## 7. 我认为一定要讲清楚的几个核心思路

这几条是后面继续开发时必须反复提醒自己的：

1. 平台侧做浅封装，核心目标是治理，不是吞掉智能体运行时。
2. 平台侧要专注权限、管理、审计、catalog 这些平台问题。
3. 智能体及 AI 相关开发，主战场就是 `runtime-service`。
4. 调试阶段优先使用 `runtime-web`，先把能力在 Runtime 层调通。
5. 调通后只要遵守契约，就可以无缝接入平台侧和 `platform-web`，不需要额外适配。
6. 后续各部分独立 Docker 部署，本质上是当前解耦设计的自然延伸。
7. `runtime-service` 已经封装好了智能体开发框架，还有现成例子，很多场景直接照着改就够了。

## 8. 这篇文档和其他记录怎么配合看

建议这样读最顺：

1. 先看主仓库 `README.md`
2. 再看这篇开发范式说明
3. 然后看部署基线记录
4. 再选单智能体案例或多智能体案例继续往下读

这样顺序最合理，因为你先知道这个项目为什么这么拆，再去看具体怎么部署、怎么开发，就不会把每篇记录都看成互相独立的零散笔记。
